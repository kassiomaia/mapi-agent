# Mapi: a personal vacation planning agent

**English** | [Português](README.pt-BR.md)

Mapi is an AI agent that helps you plan a trip. It checks flight prices, the weather for your travel dates, photos of the destination and the distance between stops, and it can put together a complete trip plan with a day-by-day itinerary, attractions, food, neighborhoods, tips and a budget.

The project is also a teaching demo of how AI agents work. Every core concept lives in the implementation: calls to the Claude Messages API, tools defined with JSON Schema, local execution of `tool_use`, the agentic loop with a step limit, a scope guardrail, and interfaces generated by the agent. The agent runs on a Node.js server with [Hono](https://hono.dev), and the browser talks to it over WebSocket. The interface is a React client built with [Agents Kit](https://agents-ui.github.io/agents-kit/) components and Tailwind CSS 4.

The agent's persona, prompts and interface are in Brazilian Portuguese; the code is in English.

## Features

| Tool | What it does | Data source |
| --- | --- | --- |
| `get_weather` | Current temperature in a city | [Open-Meteo](https://open-meteo.com) |
| `get_forecast` | Weather for a period of up to 31 days: the daily forecast for the next 16 days, and the 10-year historical average for later dates | Open-Meteo forecast and archive APIs |
| `get_coordinates` | Latitude and longitude of a city | Open-Meteo geocoding |
| `calculate_distance` | Geodesic distance between cities, drawn on a map | `geographiclib` (WGS84), Leaflet and OpenStreetMap |
| `get_city_photos` | Freely licensed photos of a city, with author and license | Wikidata, Wikipedia and Wikimedia Commons |
| `search_flights` | Reference airfare between two cities from flight comparison sites | [Tavily](https://tavily.com) web search |
| `plan_trip` | Complete trip plan, researched in parallel and composed by the model | All of the above |
| `calculate` | Basic arithmetic for budgets | Local |

On top of the tools, the chat has a few interactive pieces:

- **Live planner checklist**: while `plan_trip` runs, a list of steps is checked off and a small plane moves along a dotted route.
- **Trip plan**: cover photo, a boarding-pass style ticket, the weather for the travel dates, and tabs with the itinerary, attractions, food, neighborhoods, packing list, costs and photos. Attractions, food and neighborhoods use a bento grid with photo tiles.
- **Trip details form**: when the user asks for a plan or flights without dates or a number of travelers, the agent shows a form with a date range calendar and traveler steppers, then pauses until it is submitted.
- **Yes/No buttons**: when an answer offers a follow-up action, such as "Should I redo the plan with 5 days?", the chat shows Yes and No buttons; Yes sends the complete request.
- **Cancellation**: the Stop button aborts the model call and any tool still running on the server.

## Requirements

- Node.js 22.9 or later (tested with Node 24)
- A Claude API key, or access to Claude on Amazon Bedrock
- Optional: a [Tavily](https://tavily.com) API key for flight searches and trip plans

## Getting started

```bash
npm install
cp .env.example .env
```

Fill in `.env` with your provider and keys, then start the app:

```bash
npm start
```

The command builds the client bundle into `public/build` and starts the server. Open [http://localhost:3000](http://localhost:3000). To build only the client, run `npm run build:client`.

## Configuration

| Variable | Purpose | Default |
| --- | --- | --- |
| `ANTHROPIC_PROVIDER` | `anthropic` (Claude API) or `bedrock` (Amazon Bedrock) | `anthropic` |
| `ANTHROPIC_API_KEY` | Claude API key | required for `anthropic` |
| `AWS_REGION` | Bedrock region | required for `bedrock` |
| `AWS_BEARER_TOKEN_BEDROCK` | Bedrock API key | default AWS credential chain if unset |
| `ANTHROPIC_MODEL` | Model to use | `claude-haiku-5-5` or `global.anthropic.claude-haiku-5-5` |
| `AGENT_MAX_STEPS` | Step limit of the agentic loop | `8` |
| `PORT` | HTTP and WebSocket port | `3000` |
| `TAVILY` | Tavily API key, used by `search_flights` and `plan_trip` | without it, flight search returns an error |
| `WIKIMEDIA_CONTACT` | Email or website sent in the User-Agent to the Wikimedia APIs | unset (10 requests per minute limit) |

`.env` is ignored by git. Never commit real keys.

## How it works

### Architecture

The agent runs on the server, so API keys never reach the browser. The browser sends each question over WebSocket and receives, on the same connection, the agent's events (thinking, tool calls, results, guardrail, generated UI and progress) and the final answer. Each WebSocket connection has its own conversation.

1. **Guardrail**: a small classifier call decides whether the question can be answered with the available tools, using the conversation context to resolve references such as "those cities". Greetings are allowed so the agent can introduce itself.
2. **Agentic loop**: the model is called with the tools and adaptive thinking. While `stop_reason` is `tool_use`, each tool runs locally and its result goes back with the same `tool_use_id`, or with `is_error` when it fails. The loop stops at the step limit.
3. **Next step**: after the answer, another short call checks whether it ends with an offer the tools can carry out, and returns the Yes/No question and the full request for Yes.

### Generated UI

The agent has a presentation tool, `render_ui`. When an answer has structured data, the model calls it with a JSON interface spec (text, stats, table, list, meter, tabs and accordion blocks), which the server validates with `zod`. The model never generates code: it only fills in the spec, and the client decides how to draw it. Tabs, accordion and meter use the headless components of [UI SDK](https://ui-sdk.dev/docs).

Tools can also attach UI to their own results: a map for distances, a gallery for photos, links for flights, a weather outlook and the full trip plan. That data comes from the APIs, not from the model.

### Trip plan

`plan_trip` shows a tool that orchestrates several steps and uses the model itself:

1. **Parallel research**: geocoding, the weather for the travel dates, photos, flights, distance, and six web searches (what to see, what to eat, where to stay, practical tips, events in the period and daily budget).
2. **Composition**: the research is sent to the model with a forced call to an internal `compose_trip_plan` tool, whose `zod` schema defines the plan. The result is validated before it is shown.
3. **Values computed in code**: the time difference to Brasília and the cheapest airfare are computed from the data, not by the model.
4. **Photos**: the model gives the English Wikipedia title of each day's main place, attraction, dish and neighborhood. One request fetches all lead images and another fetches author and license from Wikimedia Commons.

Tools receive a `ToolContext` with the model client, the abort signal and a function to report progress, which the server forwards as `progress` events.

### Weather beyond 16 days

Daily forecasts only cover the next 16 days. For later dates, `get_forecast` computes the average of the same calendar dates over the last 10 years from the Open-Meteo archive, in a single request, and the interface labels it as typical weather, not a forecast.

### Flight prices

There is no free, open airfare quote API, so `search_flights` searches flight comparison sites through Tavily. Results are ranked by route, and a price is only shown when the page title names the destination. Prices are references found on the web, not real-time quotes, and the agent says so.

## WebSocket protocol (`/ws`)

Browser to server:

```json
{ "type": "prompt", "text": "Qual a temperatura em Lisboa?" }
{ "type": "cancel" }
```

Server to browser:

- `ready`: active configuration (provider, model, step limit and maximum prompt length)
- `event`: an agent event (`thinking`, `tool`, `result`, `guardrail`, `ui` or `progress`)
- `answer`: the final answer, with `blocked`, `stoppedByLimit` and `nextStep`
- `cancelled`: the run was stopped by a `cancel`; the conversation goes back to its state before the question
- `error`: an error, including invalid messages or a prompt sent while another answer is running

## Project structure

```
src/
  index.ts              entry point: reads the configuration and starts the server
  agents/               agent logic, with no interface dependencies
    agent.ts            agentic loop with step limit
    chat.ts             conversation session (history, context and guardrail)
    client.ts           model client (Claude API or Bedrock)
    config.ts           environment variable parsing and validation
    context/            conversation context as entities (cities and turns)
    decisions/          extracts the Yes/No next step from an answer
    forms/              trip details tool that pauses the agent
    generative-ui/      UI spec (zod), types and the render_ui tool
    guardrails/         scope classifier
    planner/            trip plan research, composition, progress, time zone and price
    services/           Open-Meteo, geodesy, Wikimedia, Tavily and weather outlook
    tools/              the agent's tools
  server/               Hono web server, WebSocket handling and HTML views
  client/               React client (Agents Kit and Tailwind 4), bundled with esbuild
    components/         chat, generated UI, trip plan, forms and the vendored Agents Kit
    styles/             Tailwind 4 theme and map styles
scripts/
  build-client.ts       esbuild bundle (CSS is built by the Tailwind CLI)
public/brand/           the Mapi mascot, also used as favicon
docs/prompts/           sample prompts (in Portuguese) to try the agent
```

The server and the client have separate TypeScript configs: `tsconfig.json` (Hono JSX, Node) and `tsconfig.client.json` (React JSX, DOM). Check both with:

```bash
npm run typecheck
```

## Agent concepts in the code

- **Tool**: `name`, `description` and `input_schema` as JSON Schema; the model decides when to use it.
- **tool_use**: the model asks for a call, and local code runs it.
- **tool_result**: the result, or the error with `is_error`, goes back to the model with the same `tool_use_id`.
- **stop_reason**: `tool_use` means more steps; anything else ends the loop.
- **Step limit**: keeps the agent from repeating actions forever.
- **State**: the API keeps no memory; the `messages` array is the agent's state.
- **Scope guardrail**: a classifier refuses out-of-scope requests before the agent is called.
- **Generated UI**: a presentation tool turns answers into interface, without running code from the model.
- **Human in the loop**: a form tool pauses the agent until the user provides the missing details.

## Third-party code and data

- The Agents Kit components in `src/client/components/beui/` are copied from the kit under the MIT license (see `LICENSE` and `SOURCE.json` in that folder). That code was not written for `exactOptionalPropertyTypes`, so the option is off only in `tsconfig.client.json`.
- Photos come from Wikimedia Commons under free licenses such as CC BY-SA, and the interface always shows the author and license with a link to the image page.
- Map tiles come from OpenStreetMap and follow the [OSM Foundation tile usage policy](https://operations.osmfoundation.org/policies/tiles/): fine for a demo, not for heavy traffic.
- Wikimedia limits clients without contact information in the User-Agent to 10 requests per minute. Set `WIKIMEDIA_CONTACT` to raise the limit to 200.
